# 共有をやめてから直列化を考える (Separate Before Serializing Shared State)

並行に動く処理が同じ状態を書き換えうるなら、まず同じ書き込み先が要るのかを問う。要らなければ共有をやめる。共有が本当に要るときだけ、構造で直列化する (lockファイル、段階の分離、書き手を1つに限る、compare-and-swap)。

共有された状態への並行の書き込みは、間欠的で再現しにくく、調べるのに高くつく競合を生む。決まりごとや注意書きは、並行の制御にならない。

## 基準

- 両方が読み書きするファイル、両方が書き込むkey、両方が定義して使うAPIを洗い出す
- 各処理が自分のファイル、key、directoryを持ち、読む側でまとめる。1つの状態ファイルに、各処理が別々のfieldを書くのも、共有の書き込みである
- 「lockが要る」は既定の答えにせず、共有をやめられないかを確かめる合図として扱う

## 当てはめないとき

1つの書き込み先が、本当の不変条件として要る場合。そのときは直列化を、注意書きではなく構造で行う。

## 飛ばした合図

並行に動く処理が、同じファイルや同じkeyに書いている。
