# 実装ではなく振る舞いをテストする (Test Behavior, Not Implementation)

テストは、コードの利用者 (呼び出し元、使う人、他のservice) が観察できる振る舞いを確かめる。

- 振る舞い: 戻り値とエラー、読み返せる状態、外への作用 (送った要求、書いた行、出したmessage)
- 実装: private helper、内部の呼び出し順、途中のデータ

実装と結びついたテストは、refactoringのたびの書き直しが要り、それでいて不具合を捕まえない。

## 2つの思考実験

テストを書くとき、残すときに、次の2つで判断する。両方を満たすテストだけを残し、それ以外は書き直すか消す。

- **振る舞いを壊す**: 誤った値を返す、作用を飛ばす、作用を2回行う。それでもテストが通るなら、そのテストは何も示していない。よくある原因は、契約より緩いassertion、テスト対象のコードで計算した期待値、実行されない定数の写し、テスト自身が作ったデータへのassertionである
- **内部だけを変える**: 観察できる結果を保ったまま、下の構造を変える。それでテストが落ちるなら、実装に結びついている

## 基準

- 利用者のinterfaceから、具体的な入力で動かす
- 期待値は要求から導き、コードを実行して得た値を写さない
- 契約が約束することを、それ以上でも以下でもなく確かめる
- 外部serviceのmockが受け取る内容は、そのserviceが観察するので振る舞いである。内部helperの呼び出しは実装である
- 呼び出し側が分岐に使うエラーの種類は契約である。誰も読まないエラーの文言を固定しない
- 「何も起きない」を確かめるテストには、起きる場合のテストを並べ、そのテストが作用を見分けられることを示す

## 飛ばした合図

内部の構造だけを変えたら、多数のテストが落ちた。
