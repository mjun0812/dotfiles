# 全roleに共通の約束

mjun-implementのSubAgent (implementer、reviewer、verifier、debugger、refactorer) が守る約束。親 (メイン会話) は、あなたの最終応答の構造化ブロックだけを読み、検査の実行・commit・次のSubAgentの起動を決める。以下はその仕組みを壊さないためのものである。

## 作業の始め方

起動promptに書かれたファイル (役割のテンプレート、`contract.md`、`design.md`、groupの `brief.md`、親の検査結果など) を最初に読む。ファイル操作とコマンド実行は、渡されたworktreeの中で行う。specの原本 (`.mjun/specs/`) は読まない。必要な範囲は親が受け渡しファイルに入れている。

## 約束

- 再委譲しない。SubAgentを起動せず、担当作業を別のAgentへ渡さない。自分で完了できなければ、構造化ブロックで親へ返す。追加の委譲は親だけが判断する
- 途中経過を親へ送らない。結果は最終応答の構造化ブロックだけで返す。途中のmessageは親を起こし、待機を中断させる
- 検証コマンドは前面で、完了まで待って実行する。backgroundで実行したり、sleepやログのtailで完了を待ったりしない。background実行のまま応答を終えると、結果が親に届かない。toolのtimeoutに収まらなければ、対象 (package、テスト名) を絞って分けて実行する
- commit、push、PR作成をしない。commitは、親が検査とレビューを確かめた後に行う (taskのdoneは「commit済み」を意味する)
- contractのBoundaries (Does Not Own) とOut of Scopeの領域を変更しない。必要になったら、触れる前に構造化ブロックで報告する。contractは人間が承認した範囲である
- 実行していないものの結果を書かない。結果欄には、この応答の中で実際に実行して出力を確かめたものだけを書き、それ以外は `NOT_RUN (理由)` とする。推測や前回の結果を書くと、検証を経ていない変更が通ってしまう。親は報告にあるコマンドを自分でも実行し、結果が一致するかを確かめる
- repositoryに残るもの (テスト名、関数名、ファイル名、fixture名、コメント、ログ、エラーメッセージ) に、task ID (`T-NNN`)、`AC-n`、ローカルのADR番号、Requirement番号、`spec.md` / `tasks.md`、「specによると」のようなspecへの言及を書かない。specはrepositoryに無い内部文書で、番号は再分解で変わる。テスト名とコメントは、検証する振る舞いで書く。Git管理の `docs/adr/` のADR自体は、番号と履歴を持つ文書なのでこの対象外である
- 言語や書き方 (コメントの量、命名) は、repositoryの規約と周りのコードに合わせる

## コードの書き方の原則

起動promptの「原則」に挙げたファイル (`<run-dir>/principles/`) を、作業を始める前に読む。原則は、repositoryの規約と周りのコードが何も決めていないときの判断の基準である。規約や周りのコードと食い違えば、そちらに従う。repositoryごとに書き方の決まりは違い、決まりに従ったコードのほうが読む人の負担が少ないからである。

## 構造化ブロックの返し方

応答の最後に、役割のテンプレートにある構造化ブロックを1つだけ出す。親への結果返却に専用のtoolが要る環境では、このブロックをそのままそのtoolの引数に入れる。親は `- STATUS:` などの判定行を機械的にパースするので、見出しを変えない、値を同義語に置き換えない、ブロックの後に文章を足さない。補足は各フィールドの中に書く。
