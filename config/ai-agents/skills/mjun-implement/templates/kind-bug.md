# バグ修正の観点

このgroupはバグ修正である。症状を抑えるのではなく原因を直し、報告された不具合が直ったことを、修正前後の証拠で示す。症状だけを抑えた修正は、テストが通っても別の条件で再発する。

## 証拠の段階

修正前後の証拠は、次のうち届く中で最も上の段階で取る。上ほど、後の変更でも自動で再発を捕まえられる。

1. **test**: 報告された症状をテストで再現する。そのテストは修正前に失敗し、修正後は通る
2. **observation**: テストでは症状に届かない (jsdomがlayoutを計算しない、E2Eの仕組みが無いなど) とき、briefの再現手順を実物 (実ブラウザ、CLI、script) でなぞり、修正前後の出力やスクリーンショットを取る。原因の箇所を通る処理だけを単体テストにできるなら、それも足す
3. **instrumentation**: 手元で症状が起きないとき、ログや計測を足し、発生条件を作り出し (遅延の注入、並列度や回数を上げた繰り返し)、条件を絞って、原因の仕組みが働く様子を記録する。修正後は同じ条件で、その仕組みが働かないことを記録する。足したログは報告の前に外す

testに届かない理由は、段階と一緒に `REPRODUCTION` へ書く。observationとinstrumentationでは再発を自動で捕まえられず、人間の確かめる余地も残る。そのため、そのtaskを `REVIEW_ONLY` に挙げる。

## implementer

- production codeを直す前に、上の段階で修正前の証拠を取る。testを書けるのに下の段階で済ませない
- 原因を特定してから直す。なぜその状態になるのかを1〜2文で説明でき、その説明が修正前の証拠と合うまで、修正に入らない。説明は `EVIDENCE` に書く
- `BLOCKED` にするのは、instrumentationまで試しても原因の仕組みが見えないときだけである。繰り返す回数は、報告された頻度で起きるなら1回は発生すると見込める数を目安にし、条件を変えた試行も重ねる。試した条件と回数、残った手がかりを `BLOCKER` に書く。仕組みが見えないまま、推測で修正を入れない。直ったかどうかを示せないからである
- 修正は原因の箇所に当て、変更を最小にする。再現の証拠を通すためだけの分岐 (特定の入力の特別扱い、例外の握りつぶし) を入れない
- 同じ原因で誤る箇所が他にあれば、担当の範囲内なら直し、範囲外なら `CONCERNS` に書く

## reviewer

次のどれかに証拠付きで反していれば、Acceptance Criterionの未充足 (項目9) としてREJECTする。

- `REPRODUCTION` に、段階と、修正前後の出力 (testなら失敗と成功、observationとinstrumentationなら同じ手順・条件での前後の観察) がある
- 再現の証拠が、briefの再現手順と同じ道筋で不具合を起こしている (別の条件を試すだけになっていない)。原因の箇所だけを見る単体テストは、症状の観察と組み合わさっていれば、それでよい
- testより下の段階なら、testに届かない理由が具体的で、そのtaskが `REVIEW_ONLY` に挙がっている
- 修正が、説明された原因に当たっている。症状だけを抑える分岐になっていない
- 修正と関係の無い変更 (外し忘れたログを含む) を含んでいない
