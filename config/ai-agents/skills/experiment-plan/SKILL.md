# 機械学習の実験計画書を作成する

## 目的

機械学習の実験について、実施前に目的、検証可能な仮説、判定基準を確定し、実施後に検証結果と考察を追記できる計画書を作成する。

保存先はリポジトリルートの `.mjun/experiments/` とする。

## 手順

### 1. 既知の情報を収集する

会話の文脈とコードベースを調査し、実験の目的、背景、関連実装を把握する。

### 2. 実験設計を確認する

実験設計に必要な未決事項を、一つずつユーザーに確認する。

各論点は、計画書へ反映する判断が揃ってから次へ進む。

次の順序を目安に確認し、文脈から明らかな項目は省略する。

1. **目的**：何を明らかにする実験か、なぜ今実施するのか
2. **仮説**：何が起きると予想するか、支持または反証をどの数値や基準で判定するか
3. **実験設計**：対象 (モデル、データ、設定)、比較条件 (ベースライン)、評価指標、評価セット
4. **実装**：必要な実装項目と、既存資産で対応できる範囲
5. **スコープ**：対象外とする事項、既知のリスク、関連する計画やIssueとの関係

質問では次の規則を守る。

- 質問は必ず一度に一つだけ行う。
- 各質問には、推奨する選択肢とその理由を示す。
- 利用できる場合は、`AskUserQuestion`や`request_user_input`など、ユーザーに選択を求めるツールを使う。
- 選択ツールを利用できない場合は、次の形式で選択肢を示して返信を待つ。
- 各質問の前にコードベースの関連箇所を調査し、調査で確認できる事実は質問しない。
- 必要な判断が揃ったらインタビューの終了を提案し、続行を求められた場合だけ続ける。

```text
### Q[番号]: [質問文]

1. [選択肢]
2. [選択肢]
3. [選択肢]

**推奨: [選択肢番号]**
**理由:** [推奨理由]
```

### 3. 計画内容の合意を得る

質問と回答の対応を保ったまま決定事項をまとめ、計画書へ反映する内容についてユーザーの承認を得る。

### 4. 計画書を保存する

同梱の [`assets/template_experiment_plan.md`](assets/template_experiment_plan.md) をコピーし、`.mjun/experiments/` に計画書を作成する。

- `.mjun/experiments/` がなければ作成する。
- ファイル名は `YYYYMMDD_<slug>.md` とし、作成日を日付部分に使う。
- 計画の親子関係を示す連番は付けず、本文のリンクで関係を示す。
- テンプレート内の `<...>` は適切な内容で置き換え、不要なプレースホルダは行ごと削除する。
- 計画フェーズで見出しだけ残す結果セクションを除き、空のセクションを残さない。
- メタ表の `Status` は `planning` または `in-progress` で開始する。

### 5. 整形して報告する

1. `oxfmt .mjun/experiments/` でフォーマットする (`oxfmt` がなければスキップ)。
2. 作成したファイルパス、目的、仮説を報告する。
3. ユーザーから依頼された場合だけcommitする。

## 計画書の記述規則

計画書には次の規則を適用する。

1. **計画フェーズでは結果を記入しない**：`## 実験結果` 以降は、仮説検証、考察、今後の展望を含めて見出しだけを残す。
2. **`## 実装` には実装項目だけを書く**：必要な実装項目を簡潔な箇条書きで列挙し、詳細な手順、コマンド、コードスニペットはIssueやPRで扱って、メタ表と `## 実装` のIssue一覧からリンクする。
3. **仮説を検証可能にする**：実施後に「支持」「部分支持」「反証」「検証不可」のいずれかを判定できる粒度とし、インタビューで合意した判定基準の数値と比較対象を含める。
4. **番号だけで節外から参照しない**：`H1`、`Phase 2`、`Exp 1` などの識別子を別のセクション、ファイル、メタ表、目次から参照するときは、内容が分かる名称を併記する (例: 「H1: 弱教師強化」)。
5. **目次を見出しと同期させる**：見出しを追加または削除したら目次も更新する。
