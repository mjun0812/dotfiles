# mjun-verify

テストが通っても、アプリを実際に動かすと期待どおりに動かないことがある。動かして確かめる手順がrepositoryに無いと、agentは作業のたびに起動方法と操作方法を調べ直すか、確かめずに完了を報告する。このskillは、そのrepositoryのアプリをユーザーと同じように動かして証拠を取る手順を一度だけ調べ、Git管理外の `.mjun/verify/` に書き残す。

読み手は、このアプリを見たことのないagentで、別の作業の途中にこの文書を開く。だから、一般的な例ではなく、このrepositoryで実際に動いたコマンドと、実際に観察した結果だけを書く。

検証手順を読むのはmjun系skillである。mjun-implementは、検証コマンドの洗い出しと、実装していないagentによる最終の検証で `.mjun/verify/` を使う。

## 置き場所

```text
.mjun/verify/
├── README.md           # 検証手順。起動、状態確認、操作、証拠、片付け、補助script
├── features/
│   ├── README.md       # 機能マップの索引と、全機能に共通の前提
│   └── <feature>.md    # 1機能1ファイル
└── scripts/            # 補助script。`zsh <script>` で呼ぶ
```

- スクリーンショットや出力の記録などの証拠は `.mjun/evidence/<実行ごとの名前>/` に置く。片付けで消す一時ディレクトリの中には置かない。mjun-implementは `.mjun/evidence/<branch名>/` を指定するので、置き場所は呼び出し側が指定できるようにする
- `.mjun/` はworktreeからsymlinkで共有される。補助scriptは自分の置き場所からrepositoryを決めず、実行時のcurrent directoryを検証するcheckoutとして扱う。こうすると、同じscriptで作業中のworktreeを検証できる
- `.mjun/` はglobal gitignoreでGit管理外にしてあるので、repositoryの `.gitignore` は変えない

`.mjun/verify/README.md` が既にあれば、作り直さずに [作成済みの検証手順を更新する](#作成済みの検証手順を更新する) へ進む。

## 手順

1. **repositoryを調べる**: 次の5つをコードと文書から答える。ユーザーに聞くのは、外部サービスの認証情報のように、コードから観察できないことだけにする
   - 面: ユーザーが実際に触るもの。web UI、CLI、TUI、desktop app、API、libraryのどれか。複数あれば主な面を1つ決め、残りも書き留める
   - 起動: repositoryが文書にしている開発用の起動方法。package script、Makefile、READMEのquickstartから探す。port、環境変数、seed data、認証も調べる
   - 操作: agentがプログラムから操作する手段。E2Eテストのspec、PTYのhelper、curlで呼べるendpointのように、repositoryに既にある仕組みを先に使う。無ければ、webとElectronはbrowserの自動操作にし、Skill toolで `agent-browser` を呼ぶ。CLIとTUIはtmuxかPTY、serviceはHTTPにする
   - 観察: 取れる証拠。スクリーンショット、terminalの記録、response、ログ、終了コード、保存されたデータ
   - 隔離: portやデータの置き場を分けて、2つのインスタンスを並べて動かせるか。既定の置き場がユーザーの実データなら、検証用の置き場へ必ず切り替える。並べて動かせないなら、検証手順にそう書く
2. **そのまま動くことを確かめる**: checkoutが手を入れずにbuild・起動できなければ、原因を特定して報告し、ここで止める。動かないコードに合わせて書いた手順は、誤った手順として残る
3. **検証手順を書く**: [templates/verify.md](templates/verify.md) の見出しをすべて埋めて `.mjun/verify/README.md` を書く。コメントの指示に従い、コメントとplaceholderは残さない
4. **機能マップを書く**: ユーザーから見える機能を、routes、コマンド、メニュー、文書から拾い、主なもの3〜5件を [templates/feature.md](templates/feature.md) の形で `features/<feature>.md` に書く。`features/README.md` には、索引、全機能に共通の前提、操作の約束を書く。共通の前提には、基準にする状態とseed dataを含める。機能ファイルの「到達方法」には、UI、キーボード、CLI、APIのうち、その機能に届くものをすべて挙げる。都合のよい1つだけを動かした証明は、他の到達方法に不具合があっても通るからである
5. **通しで動かして証明する**: 書いた手順を、自分でそのとおりに1回実行する。起動、状態確認、機能1件の操作、証拠の取得、片付けの順に行い、片付けの後に証拠が `.mjun/evidence/` に残っていることを確かめる。失敗した箇所は手順を直してやり直し、失敗した回の後にも片付けを実行する。途中で止まった試行がprocessやportを残さないようにするためである。一度も実行していない手順は下書きであり、成果物として渡さない
   - seed dataに足りない前提があって操作が完了しないときは、操作を弱めて通さない。失敗として報告し、理由をその機能の「注意点」に書く
   - 本番のstackの代わりにlocalのstackを使うなど、本物の環境の代わりで証明したときは、代わりの環境だけが行った準備を列挙する。それらは未検証として残る
6. **報告する**: 書いたファイル、通しで動かした機能と証拠のパス、動かしていない機能、検証中に見つけたアプリの不具合を示す。不具合は直さずに報告だけする

## 作成済みの検証手順を更新する

アプリが変わると、機能マップは古くなる。更新では `.mjun/verify/` の中だけを編集し、アプリのコードは変えない。

1. `features/README.md` の索引と機能ファイルを比べ、欠け、余り、重複を直す
2. 最近の変更で増えたユーザー向けの機能を、コードの場所を確かめてから機能マップに足す
3. 検証手順どおりに起動し、すべての機能を1回ずつ操作する。予想外の動きをした後は、状態確認をやり直してから次を操作する
4. 食い違いを分類して扱う
   - 文書の誤り: 到達方法や結果の記述がアプリと違う。文書を直す
   - 操作の手段の不足: 動いている振る舞いを操作できない。補助scriptか手順を直し、直した手段でもう一度操作して確かめる
   - アプリの不具合: 文書どおりに動くはずの振る舞いが動かない。文書を合わせず、不具合として報告する
5. 到達できない機能は、試した到達方法と足りない前提を添えて報告する。前提は、認証、権限、OS、外部の状態などである。機能マップにその前提が無ければ、足す
6. 片付けの後に証拠が残っていることを確かめ、直したファイル、操作した機能、到達できなかった機能、見つけた不具合を報告する
