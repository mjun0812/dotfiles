# Research

decisionに必要な外部事実の不足を、ユーザーへの質問ではなく一次資料の調査で埋める手順。1回の調査で扱う質問は1つだけとし、調査は判断材料の提供までに留める (decisionの分類と決定はPhase 3に戻って行う)。

## 原則

- **出典の信頼度**: 次の3階層で扱う
  - Tier 1: 標準仕様、対象ライブラリのソースコード、公式ドキュメント・first-partyのAPIリファレンス
  - Tier 2 (first-party artifacts): changelog / release notes、issue trackerのmaintainer発言、テストコード、git履歴
  - Tier 3 (secondary): 解説記事、第三者ベンチマーク、Q&Aサイト、コミュニティの報告
- **Tier 1/2を優先する**: Tier 1/2で確認できる主張はTier 3を根拠にしない。Tier 3は資料の所在探しの手がかりに使い、Tier 1/2に記述の無い経験的な主張 (運用上の問題、メンテナンス状況、計測した性能など) に限って根拠にする。その場合は `Source` にTier 3であることと、参照した件数・報告の一致度を書く
- **undocumented behaviorを区別する**: ソースコードで確認できるがドキュメントに無い挙動は、主張に `undocumented` と印を付ける
- **バージョンを特定する**: 対象リポジトリが使うバージョン (lockfile、manifest) を確かめ、それに対応する資料を読む
- **事前知識は仮説に留める**: 事前知識は確認の優先順位を決めるためだけに使う。古い可能性を前提に、確信が持てない点・変わっていそうな点から先にTier 1/2で確かめる
- **主張ごとに出典を付ける**: URL・ファイルパス・仕様の節番号と、参照日またはドキュメントのバージョン・commit hashを添える。出典を示せない主張は「未確認」として区別する
- **矛盾を明示する**: ドキュメントとソースコードの食い違いや、バージョン間の違いは、どちらかに寄せずに両方を出典付きで書く

## 手順

1. 質問を、答えの形が定まる1文にする。複数の質問が含まれていれば分ける
2. 事前知識から答えの仮説を立て、確認すべき事実を列挙する。確信が持てない点・古くなっていそうな点を先頭に置く
3. 対象リポジトリの依存とバージョンを確かめ、読むべきTier 1/2の資料を特定する
4. 資料を調べる。WebSearchは資料の所在探しに使い、英語と日本語の両方で検索する
5. 記録する前に次を確かめ、欠けがあれば手順4に戻る
   - 手順1の質問に答えきれているか。手順2の事実に未確認のものが残っていないか
   - 結論を覆しうる直近の変更 (release notes、deprecation、破壊的変更) を確かめたか
   - 主要な主張に対して、Tier 1/2の中に反例や矛盾する記述がないか
6. `.mjun/specs/<slug>/research/<topic>.md` (`<topic>` は内容を表す英語kebab-case) に次の形式で保存し、該当decisionのEvidenceからこのファイルを参照する。GitHub Issueへは投稿しない

```markdown
# Research: <topic>

## Question

<調査した質問>

## Findings

- <主張 1>
  - Source: <URL / path / 仕様の節> (<参照日 または version / commit hash>)
- <主張 2> (undocumented)
  - Source: <ソースコードのpath> (<commit hash>)
- <経験的な主張>
  - Source: Tier 3。<URL 1>、<URL 2> (<参照日>)。<件数>件中<件数>件が一致
- <資料間で食い違う主張>
  - Doc: <ドキュメントの主張> — Source: ...
  - Code: <ソースコードの挙動> — Source: ...

## Unresolved

- <どの階層の出典でも確認できなかった点。なければ「なし」>

## Implication

<このdecisionに対して調査結果が示唆すること (推奨ではなく含意)>
```
