# 承認用HTMLの構成

Phase 5で「HTMLで内容を確認する」が選ばれたときに作る解説ページ。判断シートだけでは掴みにくい構成の変化を、図で補う。人間が「何を、どう作るのか」を理解して承認を判断できるよう、全体像から細部へ順に説明する。contractとdesign.mdの原文を転記しない (ページの役目は理解を助けることにある)。

## 作り方

- Skill toolに `exhtml` があれば、このファイルの内容と素材を渡して作らせる。無ければその場で1枚の自己完結HTMLを書く (図はインラインSVG)
- `/tmp/YYYY-MM-DD-<slug>-spec.html` に保存し (spec配下には置かない)、`open` で開く

## 素材

`spec.md`、`design.md` (`## Decisions` を含む)、関係するADR、Phase 2で読んだ現行コードの構造 (変更前の姿を描くため)。承認の判断材料なので、素材に無い設計や推測を書き足さない。必要な事実が素材に無ければ、その旨を本文に書く。

## 本文の構成

上から順に置き、該当する内容が無いセクションは省く。

1. **何を解決するか**: ContextとGoalを2〜3文で言い換え、冒頭に「何が変わるか」「どう作るか」「主な判断」を1項目ずつ置く
2. **全体像**: 変更前後の構成を並べた図。Modulesの新設・変更と既存の仕組みとの関係、触る部分と触らない部分 (Boundaries) を示す
3. **処理の流れ**: Data Flowの図 (往復はsequence図、分岐はflowchart、状態は状態遷移図)。各段階で起きることを図の後に散文で補う
4. **設計判断**: 主要なdecisionごとに論点、採択案、却下案、理由を並べる。ADRは出典として添える
5. **変更範囲**: Change Outlineをdirectory treeの差分で示し、新設と変更を区別する
6. **検証の見通し**: 各ACを、どのmoduleのどの振る舞いで満たし、どの層で確かめるか (Test Strategy) と対応づける。ACの文面は短く要約する
7. **リスクと未確定事項**: Revalidation Triggers、Trial Implementation Notesの問題点、誤解されやすいOut of Scope

「全体像」と「処理の流れ」の図は省かない。文章だけでは構成の変化を読み取りにくく、承認の判断が表面的になる。図のラベルにはspecと同じ語彙 (用語集があればその語) を使い、変更前後の比較では新設・変更・既存の塗り分けとその意味を示す。
