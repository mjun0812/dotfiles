# 承認用HTMLの構成

Phase 5で「HTMLで内容を確認する」が選ばれたときに作る解説ページの規則。人間が「何を、どう作るのか」を理解して承認を判断できるよう、全体像から細部へ順に説明する。contractとdesign.mdの原文は転記しない。

## 作り方

- Skill toolに `exhtml` があれば、このファイルの内容と素材を渡して作らせる。無ければその場で1枚の自己完結HTMLを書く (図はインラインSVG)
- `/tmp/YYYY-MM-DD-<slug>-spec.html` に保存して (spec配下には置かない) `open` で開く

## 素材

- `spec.md` と `design.md`
- `design.md` の `## Decisions` と、関係するADR
- Phase 2で読んだ現行コードの構造 (変更前の姿を描くため)

素材に無い設計や推測を書き足さない。必要な事実が素材に無ければ、その旨を本文に書く。

## 本文の構成

上から順に置き、該当する内容が無いセクションは省略する。

1. **何を解決するか**: ContextとGoalを2〜3文で言い換え、冒頭に「何が変わるか」「どう作るか」「主な判断」を1項目ずつ置く
2. **全体像**: 変更前後の構成を並べた図。Modulesの新設・変更と既存の仕組みとの関係、触る部分と触らない部分 (Boundaries) を示す
3. **処理の流れ**: Data Flowの図 (往復はsequence図、分岐はflowchart、状態は状態遷移図)。各段階で起きることを図の後に散文で補う
4. **設計判断**: 主要なdecisionごとに論点、採択案、却下案、理由を並べる。ADRがあれば出典として添えるだけにする
5. **変更範囲**: Change Outlineをdirectory treeの差分で示し、新設と変更を区別する
6. **検証の見通し**: 各ACを、どのmoduleのどの振る舞いで満たし、どの層で確かめるか (Test Strategy) と対応づける。ACの文面は短く要約し、全件の表だけで済ませない
7. **リスクと未確定事項**: Revalidation Triggers、Trial Implementation Notesの問題点、誤解されやすいOut of Scope

## 図

- 「全体像」と「処理の流れ」の2枚は必ず描く。1枚に収まらなければ主題ごとに分ける
- ラベルにはspecと同じ語彙 (用語集があればその語) を使う
- 変更前後の比較では新設・変更・既存を色で塗り分け、色の意味をキャプションに書く
- 図の直後に、その図から読み取ってほしいことを1〜2文で書く
