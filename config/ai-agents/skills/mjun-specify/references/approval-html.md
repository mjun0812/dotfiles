# 承認用HTMLの構成

Phase 6で「HTMLで内容を確認する」が選ばれたときに作る解説ページの規則。

目的は、人間が「何を、どう作るのか」を理解して承認を判断できるようにすることである。
contractとdesign.mdの原文はチャットとspecファイルで読めるため、HTMLへ転記しない。
セクションの羅列ではなく、変更の全体像から細部へ順に説明する。

## 素材

- `spec.md` と `design.md`
- specが参照する決定記録 (`Decisions:` 行のD番号) の採択案、却下案、理由
- Phase 2で読んだ現行コードの構造 (変更前の姿を描くために使う)

素材に無い設計や推測を書き足さない。説明のために必要な事実が素材に無い場合は、その旨を本文に書く。

## 本文の構成

上から順に置く。該当する内容が無いセクションは省略する。

1. **何を解決するか**: ContextとGoalを2〜3文で言い換える。冒頭要約には「何が変わるか」「どう作るか」「主な判断」を1項目ずつ置く
2. **全体像**: 変更前と変更後の構成を並べた図。Modulesの新設・変更と、それらと既存の仕組みとの関係を示し、触る部分と触らない部分 (Boundaries) が一目で分かるようにする
3. **処理の流れ**: Data Flowを図にする。登場人物の往復はsequence図、分岐のある処理はflowchart、状態を持つものは状態遷移図にする。図の後に、各段階で何が起きるかを散文で補う
4. **設計判断**: 主要なdecisionごとに、論点、採択案、却下案、採択の理由を並置する。読み手が「なぜこの作りなのか」を追えることを優先し、D番号は出典として添えるだけにする
5. **変更範囲**: Change Outlineをdirectory treeの差分で示す。新設と変更を区別する
6. **検証の見通し**: Acceptance Criteriaを、どの部品のどの振る舞いで満たし、どの層で検査するか (Test Strategy) と対応づけて説明する。ACの文面は短く要約し、全件を表に並べるだけにしない
7. **リスクと未確定事項**: Revalidation Triggers、Trial Implementation Notesの落とし穴、Out of Scopeのうち誤解されやすいもの

## 図

- 最低でも「全体像」と「処理の流れ」の2枚を描く。1枚の図に収まらない場合は主題ごとに分ける
- 図のラベルにはspecと同じ語彙 (用語集 `CONTEXT.md` があればその語) を使う
- 変更前後の比較では、新設・変更・既存をカテゴリ色で塗り分け、色の意味をキャプションに書く
- 図だけで済ませず、図の直後にその図から読み取ってほしいことを1〜2文で書く
