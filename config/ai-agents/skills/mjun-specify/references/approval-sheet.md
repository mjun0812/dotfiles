# 判断シート

Phase 5で人間に見せ、承認を取る1画面の要約。人間は `spec.md` と `design.md` を読まずに、このシートだけで「この範囲と判断で作ってよいか」を決める。だから、シートに無い内容は人間が承認していない内容になる。文書の文章を縮めるのではなく、人間の判断が要る点を拾い出して書く。

## 形式

チャットにこの順で出す。1項目を1〜2行にし、全体を40行程度に収める。該当が無い項目は「なし」と書いて残す (無いことも判断材料になる)。

```markdown
## 判断シート: <Title>

- 目的: <何がどう変わるか。1〜2文>
- やること: <Ownsの要点>
- やらないこと: <Out of ScopeとDoes Not Ownのうち、誤解されやすいもの>

### 人間が決めたこと

- <decisionの見出し>: <決定>

### agentが決めたこと (覆したいものだけ指摘してください)

- <decisionの見出し>: <採択案> (<理由を一言>)

### 動作の例

- <操作や入力> → <観察できる結果>
- 試作の画面: <`.mjun/specs/<slug>/prototype/` のパス>

### 人間の目で確かめること

- <目視の確認シナリオ。実装後にPRの画像で確かめる>
- <コマンドで判定できず、手動確認になるもの>

### 残る不確実性

- <Revalidation Triggers、試作や最小実装で見つかった問題、`ADR: 要作成` の判断>

- task: <件数>件 (<各taskのタイトルを読点区切り>)
- 文書: `.mjun/specs/<slug>/spec.md`、`.mjun/specs/<slug>/design.md`
```

## 項目の拾い方

- **agentが決めたこと**: `Owner: agent` のdecisionを省かずに1行ずつ並べる。人間は全文を読まないので、ここに無い決定は覆す機会が無い
- **動作の例**: Requirementsのうち外から見える振る舞いを、代表的な入力と結果の組で示す。文章の要求より、例のほうが速く正誤を判断できる。UIの試作をした論点は、選ばれた案の画像のパスを置く
- **人間の目で確かめること**: `design.md` のTest Strategyにある目視の確認シナリオと、コマンドで判定できないAcceptance Criteria。人間の作業になるので、承認の前に知らせる
- 外から見える振る舞いを決めるRequirementとAcceptance Criteriaは、どれもシートのいずれかの項目で扱う。扱われないものがあれば、その振る舞いを人間が見ないまま承認することになるので、該当する項目へ足す
- spec reviewの指摘を反映して変わった行には `(review)` を付ける
