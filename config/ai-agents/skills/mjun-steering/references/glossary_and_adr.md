# 用語集とADR

## 保存先と責務

- 用語集はrepo直下の `CONTEXT.md` を優先し、無ければ `.mjun/CONTEXT.md` を使う。用語が確定したら `**用語**: 定義 (1〜2文)` と `_Avoid_: 使わない言い換え` を追記する。実装詳細は書かない。
- ADRはADRディレクトリ (Git管理へ移行済みなら `docs/adr/`、それ以外は `.mjun/steering/adr/`) に1件1ファイル (`NNNN-<slug>.md`) で置く。ディレクトリは最初のADRを書くときに作る。
- Git管理へ移行済みとは、`docs/adr/` に `# ADR-NNNN:` 見出しを持つファイルがある状態を指す。他の形式の既存ADRだけがある `docs/adr/` は移行済みと見なさない。
- specの中で閉じる判断はADRにせず、そのspecの `design.md` の `## Decisions` に書く。
- core / custom steeringは現在の実装に裏付けられたパターンを記録し、ADRは判断の理由を記録する。ADRをコードから再生成したり、コードに合わせて理由を書き換えたりしない。

## ADRにする基準

次の3条件をすべて満たす判断だけをADRにする。1つでも欠ければ書かない。

1. **覆しにくい**: 後で考えを変えるコストが大きい
2. **文脈なしでは意外**: 将来の読み手がコードを見て「なぜこうしたのか」と疑問に思う
3. **本物のtrade-offの結果**: 実際に代替案があり、特定の理由で選んだ

該当しやすいもの: アーキテクチャの形、context間の連携方式、lock-inを伴う技術選定 (DB、message bus、認証基盤、deploy先など。ただし数日で替えられるlibraryは除く)、境界と所有の決定 (「やらない」の決定を含む)、自明な道からの意図的な逸脱、コードに現れない制約 (compliance、外部契約の性能要件など)、理由が自明でない却下案。

判断を確定させたagentは、3条件を満たすと判断したらユーザーに確認せずADRを書く。ただしspecの中で決めた判断は、`design.md` の `## Decisions` に `ADR: 要作成` と印を付けておき、そのspecの配送時に書く (実装されなかった判断をADRにしない)。

## ADRの書式

```markdown
# ADR-NNNN: <判断を表す短いタイトル>

<1〜3文: 文脈、決めたこと、その理由>
```

- 番号はADRディレクトリ内の既存ファイルの最大番号 + 1とする (他の形式の既存ADRを含む)。ファイル名は4桁ゼロ埋めの番号と、タイトルを英小文字・数字・ハイフンで要約したslugにする。作成直前にディレクトリを読み直す。branchのmergeで番号が重複した場合は、後から追加された側を最大値 + 1へ振り直して参照を揃える
- 次の節は価値があるときだけ足す: `Status:` 行 (`accepted` 以外になったときだけ。`superseded by ADR-NNNN` / `deprecated`)、`## Considered Options` (却下案を覚えておく価値があるとき)、`## Consequences` (自明でない波及があるとき)
- 内部文書 (`.mjun/` 配下) のパスを根拠として書かない。必要な根拠は本文に要約する

## 読み取りと変更

- 読み手は `Status:` が `superseded` / `deprecated` のADRを現在の規約として適用しない。それ以外のADRはプロジェクト全体の制約として読む。
- ADRに反する要求はHuman-owned decisionとして確認する。ADRを覆す場合は新しいADRを書き、旧ADRには `Status: superseded by ADR-NNNN` の行だけを足す。既存ADRの本文は書き換えず削除しない (保存先移行と番号の振り直しを除く)。
- codeとADRが食い違う場合は、未実装の計画かどうかを確かめる。実装済みの判断への違反はCode Driftとして報告して人間に確認する。

## Git管理へ移す場合

- 対応は `.mjun/CONTEXT.md` からrepo直下の `CONTEXT.md`、`.mjun/steering/adr/` の各ファイルから `docs/adr/` の同名ファイル。ユーザーがGit管理への移行を依頼した場合だけ実施する。`docs/adr/` や他の形式の既存ADRの存在だけでは切り替えない。
- 移行はメインrepositoryの作業ツリーで行う。supersededを含む全ADRを移し、番号と履歴を維持する。移行先の既存ADRは削除・上書きしない。番号が衝突するADRは移行先の最大番号 + 1から振り直し、ファイル名・H1・`superseded by`・steeringからのリンク・specの `design.md` の `ADR:` 行を新番号へ揃える。定義・判断内容の衝突は人間へ確認する。
- 移行先をGit管理対象にし (未追跡ならstageする。移行だけを理由にcommit・pushはしない)、用語・判断の欠落が無く、参照が解決することを確かめてから、対応する移行元ファイルだけを削除する。失敗・中断時は元を残し、完了と報告しない。未公開情報を含む場合は公開範囲をユーザーへ確認する。
- 移行完了後はGit管理側だけを読み書きし、旧ファイルを再作成しない。両方にADRが残っていたら追記を止め、移行未完了として報告する。worktreeでの作業では、Git管理側のADRを作業中のworktreeで読み書きし、そのbranchのcommitに含める。

## 履歴の発掘

- 理由が明文の判断だけを発掘し、上の3条件を満たすものだけをADRにする。コードから分かる使用技術だけで採用理由を推測しない。その事実はtech.mdやcustom steeringへ記録する。
- 判断内容が既存ADRと同じなら重複作成しない。core / customから判断の理由を参照するときは該当ADRへリンクする。
- 用語集は追記専用。specの終了・削除時にもADRは削除しない。
