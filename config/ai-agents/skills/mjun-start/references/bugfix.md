# バグ修正

原因を特定し、報告された不具合を再現するテストで直ったことを示し、同じ原因での再発を防ぐことを重視する。症状だけを抑えた修正は、完了条件を満たしても別の条件で再発する。

## briefに集めること

- **再現手順**: 実行するコマンドや操作と、入力・環境。Issueやユーザーの報告から取る。足りなければ調べて補い、報告者しか知らないこと (手元の環境など) だけを人間に聞く
- **期待する動作と、その根拠**: 期待を定めている文書・コード・テストの `file:line` か引用。根拠が見つからなければ、それは仕様の判断なので新規機能へ切り替える
- **実際の動作**: 再現手順をすぐ実行できるなら実行し、出力を記録する。不具合が今も起きることを先に確かめておくと、既に直っている報告や再現しない報告に実装の時間を使わずに済む。実行に準備が要るなら、implementerに任せる
- **原因の見当**: 分かる範囲で書く。確定させなくてよい
- **完了条件**: 「報告の手順を踏むと期待する動作になる」を、再現テスト (届かなければ再現手順の観察) が判定できる形にする。既存のテストが通ることも含める。テストで届かない見込み (実ブラウザでしか出ない、手元で再現しない) は、`## 原因の見当` に添えておく

## 実装で確かめられること

mjun-implementは、briefが `kind: bug` のとき、implementerとreviewerに [バグ修正の観点](../../mjun-implement/templates/kind-bug.md) を読ませる。修正前後の証拠は、再現テスト、実物での観察、計測の順に、届く中で最も上のもので取る。テストに届かないときも止まらずに進み、結果は人間が確かめる項目として報告に残る。reviewerは、その証拠が報告の道筋で不具合を起こしていることと、修正が原因に当たっていることを確かめる。
