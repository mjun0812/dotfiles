# 評価基準の詳細

skill-reviewの仕様チェックと観点1〜11の判定基準。

判定の優先順は次のとおり。

1. 根拠のある「要改善のシグナル」が1つでもあれば要改善
2. 観点は適用されるが必要な証拠を取得できなければ判定保留
3. 観点が適用されなければ該当なし
4. 上記以外で「合格の条件」を満たせば合格

## 仕様チェック

観点1〜11の前に、SKILL.mdがAgent Skillsの基本仕様へ適合しているかを検証する。
クライアント固有frontmatterは、対象クライアントの仕様で別途検証し、未対応クライアントが無視するfieldという理由だけでは仕様不適合にしない。

適合の条件:

- SKILL.mdがYAML frontmatterとMarkdown本文で構成されている
- `name`が存在し、1〜64文字の小文字英数字とハイフンだけで構成されている
- `name`がハイフンで始まらず、終わらず、連続するハイフンを含まず、親ディレクトリ名と一致する
- `description`が存在し、1〜1024文字である (文字数は `scripts/check_description_length.sh <path>...` で機械的に判定する)
- `compatibility`が存在する場合は1〜500文字である
- `metadata`が存在する場合は文字列キーと文字列値のmappingである
- Markdown本文が空ではない
- クライアント固有frontmatterが、対象クライアントの現行仕様に沿った構文で書かれている
- `allowed-tools`が、skillの実行に必要なtoolとコマンド範囲だけを許可している
- 読み取り専用skillの`allowed-tools`が、書き込みや破壊的操作を広く許可していない

不適合のシグナル:

- frontmatterをYAMLとして解析できない、または閉じる`---`が無い
- 必須fieldが無い、型が違う、文字数や命名規則に違反している
- `name`と親ディレクトリ名が一致しない
- Markdown本文が無い

利用可能なら対象仕様のvalidatorを実行する。
validatorを利用できない場合は上記を手作業で検証し、その旨を根拠に記載する。

## 1. 目標と境界

合格の条件:

- skillの目的(何の問題を解決するか)が冒頭付近で簡潔に述べられている
- 具体的な作業手順や内部動作について述べず、skillが実現することのみを記述する
- descriptionに書かれている発動条件と、本文の目的が矛盾していない
- descriptionの書き写しはせず、descriptionよりも詳細な目的を述べる

要改善のシグナル:

- 目的の記述が無く、手順の羅列から推測するしかない

良い例:

```text
## 目的
ドキュメントと実装の乖離を検出して更新するSkill。
```

## 2. description品質

frontmatterの`description`はskillを発動するかどうかの判断材料になる。
本文を読まなくても発動判断ができることが基準。

合格の条件:

- 何をするskillかが1文目で分かる
- 発動すべき典型的な依頼フレーズが含まれる(例: 「〜して」と依頼したら使うこと)
- 誤発動しやすい隣接ケースがあるなら「〜の場合は使わない」が書かれている
- 同じリポジトリまたはskill配置ルートにある他skillと、発動対象が衝突していない
- 具体的な作業手順や内部動作について述べない
- 冗長な表現は避け、Token数が小さくなるようにする

要改善のシグナル:

- 機能説明のみでトリガー条件が無い
- 他のskillのdescriptionと発動条件が重複・衝突している
- 文字数が1024を超えている (`scripts/check_description_length.sh` の結果で判定し、文数では判定しない)

競合の判定方法:

- 評価対象と同じリポジトリまたはskill配置ルートにある他skillの`name`と`description`を列挙する
- 同じユーザー意図で複数skillが発動し得るのに、優先関係や境界をdescriptionから判別できない場合を競合とする
- 一般的な単語が共通するだけで、対象タスクや成果物が異なる場合は競合としない
- 比較範囲を特定できない場合は、description単体の評価結果を根拠に示した上で観点2を判定保留にする

悪い例:

```yaml
description: PRを作成するSkill。
```

良い例:

```yaml
description: >-
  現在のbranchからPull Requestを作成するSkill。
  ユーザーが「PR作って」「pull request作成して」と依頼したら使うこと。
  レビューは行わない。
```

## 3. コマンド例の量

AIはコマンド自体の使い方を学習で獲得し、知っているため、例は最新のツールを使う場合や、
情報を追加する場合にだけ価値がある。

合格の条件:

- コマンド例が次のいずれかを明確にする場合にだけ存在する
  - 入力・出力の形式
  - 操作の順序
  - 境界ケース

要改善のシグナル:

- `git status`, `ls` など自明なコマンドの例が並んでいる
- 同じ趣旨の例が網羅性のために複数ある

## 4. 完了条件

合格の条件:

- 何をもって成功とするかが定義されている(例: 「レポートを出力して終了」「テストが通ること」)
- 最終的にユーザーへ何を提示するかが分かる
- commit、push、Issue/PRの作成、外部サービスへの書き込みなど、skillが行う副作用の有無と範囲が本文から読み取れる

要改善のシグナル:

- 手順が途中で終わっていて、成果物や終了状態が不明
- 副作用の範囲(commitするのか、pushまでするのか、外部へ投稿するのか)が不明

## 5. 早期リターン

前提が満たされない状況で作業を続けるとトークンを浪費する。

合格の条件:

- 前提条件(対象ファイルの存在、リポジトリであること、必要コマンドの存在など)を最初に確認し、満たさなければ即終了する手順がある

要改善のシグナル:

- 前提が壊れているケースへの言及が無く、失敗したまま手順を続ける余地がある
- 前提チェックが手順の後半にある

該当なしの条件:

- 前提となる外部状態が実質的に存在しないskill(純粋な文章作成など)

## 6. 自己完結性

まず対象がオーケストレーションskill (2つ以上のskillやSubAgentを呼び出して連結することが目的のskill) かどうかを判定し、
種別ごとに以下の基準を適用する。

共通の合格の条件:

- 参照するテンプレート・基準・スクリプトなどの付属ファイルをskillディレクトリ内に持つ。どのskillにも属さない共有ファイル (リポジトリ共通のテンプレート、md、ライブラリ) は参照せず、必要な内容をskill内へ複製する。他のskillのファイル (共有規則を持つ他skillのreferenceなど) も参照せず、必要な内容をskill内へ複製する
- 外部URLを参照しない。ドキュメントや仕様の内容が必要なら、必要な部分をskill内の付属ファイルへ複製する
- 外部サービス (GitHubなど) への依存は、skillの目的に不可欠な場合だけ許可する。利用方法や認証手順はskill内で完結させる

共通の要改善のシグナル:

- skillディレクトリ外にある共有ファイルへの参照がある
- 本文や付属ファイルに外部URLへの参照がある

### 通常のskill

合格の条件:

- 本文に他のskillへの言及が無い。委譲・参照だけでなく、「〜の場合は他のskillを使う」のような振り分け案内やスコープ境界の説明としての言及も含む
- 手順が自分のSKILL.mdと付属ファイルだけで完結している
- 発動時の振り分け(「〜の場合は使わない」)はfrontmatterのdescriptionに書く(観点2の領分)。

要改善のシグナル:

- 本文に他のskill名への言及がある(振り分け案内・「〜は別skillの担当」のような境界説明を含む)
- 手順の途中で「詳細は〜skillを参照」のように他skillの本文へ依存している
- 依存skillが無いと単体で成立しない

### オーケストレーションskill

合格の条件:

- 呼び出すskillの名前と実行順序が明記されている
- 連結先skillの手順の中身を本文に複製・再説明していない
- 連結先で共有すべき決定(出力言語、作業ディレクトリ、push先など)を親で1回決め、引き継ぎとして明示的に渡している
- 親が作成した一時リソース(worktree、branch、一時refなど)のクリーンアップが、成功時と中断時の両方で定義されている
- 疎結合の原則に基づき、skill呼び出し周辺以外でそのskillへの言及をできるだけせず、最小限にする。本文中の他skill名は、そのskillのリネーム・削除で気づかれずに腐るため、極力書かない。

要改善のシグナル:

- skillへの委譲が1つだけである (SubAgentは数に含めない。単一skillへの委譲は単なるラッパーであり、通常skillとして書くべき)
- 呼び出し順序や、間で受け渡す情報が不明
- 親とサブskillが同じ決定(言語判定など)を別々に行う余地がある
- 一時リソースの後始末が成功時しか定義されていない、または定義が無い

## 7. 簡潔さ

合格の条件:

- SKILL.md本文が目安500行以下
- 各セクションが目的に対して必要な情報だけを含む

要改善のシグナル:

- 同じ指示の言い換え・繰り返しがある
- 起こり得ないケースへの防御的な指示が多い。コードで言うと過剰なassertや例外処理のような冗長さがある

## 8. 分割

合格の条件:

- 長い出力テンプレート・大量の例・詳細な基準表がreferences/等の別ファイルに分離され、本文からリンクされている
- 本文には「いつそのファイルを読むか」が書かれている
- 参照はSKILL.mdから1段まで(referenceファイルからさらに別ファイルへ連鎖させない)

要改善のシグナル:

- 数十行を超えるテンプレートや例が本文に直接埋め込まれている
- referenceファイルが別のreferenceファイルへ参照を連鎖させている

該当なしの条件:

- 本文が短く、分割する対象が存在しない

## 9. 可読性

合格の条件:

- 見出し構造が手順の流れと一致している
- 表・リスト・コードブロックが適切に使い分けられている
- 人間が読んで手順を再現できる
- 本文の指示が言い切り調(「〜する」「〜しない」「〜すること」)で書かれている。ユーザーへ表示・投稿する文言のテンプレート、例文、引用の中はですます調でよい
- Phase, 手順, 節などの参照表記が統一されている
- 引用や参照は人間の注意を引くために、地の文と明確に区別されている

要改善のシグナル:

- 1セクションに無関係な話題が混在している
- 手順の番号や参照(「手順3で〜」)が実際の構成とズレている
- 同一対象への参照表記が混在している(「3節」と「Phase 3」の併用など)
- 地の文の指示にです・ます・ください調が混在している
- 引用や参照が地の文と区別されていない
- 引用や参照が文中に多く、人間の注意を散漫にする

## 10. 鮮度

合格の条件:

- 本文が参照するファイルパス・スクリプト・付属ファイルが実在する
- 本文が前提とするコマンドが実在する(バージョン差異までは問わない)
- 付属スクリプトにLinter・Formatter (shell: `shellcheck`, `shfmt -d` / Python: `ruff check`, `ruff format --check`。Formatterのオプションはリポジトリのformatter設定に従い、無ければ既定で実行する) を適用して、警告も整形差分も出ない
- 付属スクリプトを副作用の無い引数 (`--help`、dry-run、読み取り専用の操作) で実行して、動作する

要改善のシグナル:

- リンク先のreferencesファイルが無い
- 存在しないパスやリネーム済みのコマンドを参照している
- 付属スクリプトにLinterの警告、またはFormatterの整形差分が出る
- 付属スクリプトが動作しない

判定方法: 本文からパス・コマンド名を抽出し、実在を確認する。付属スクリプトにはLinter・Formatterを適用し、副作用の無い引数で実行する。
外部URLは到達確認せず、参照が存在すること自体を観点6で指摘する。

## 11. クライアント互換性

skillは複数のagentクライアントで共有される場合がある。
`allowed-tools`などのクライアント固有frontmatterは、未対応クライアントで無視されること自体は問題としない。
主要なクライアントが共通に持つ機能 (skill、SubAgent、AskUserQuestionのようなユーザーへの選択質問ツール) については、代替手段を用意しなくてよい。

合格の条件:

- 手順が特定モデルの固有機能に依存する場合は、対象環境が明記されているか、代替手段または「無ければスキップ」が書かれている
- 手順が具体的で、推論力の低いモデルでも順に実行すれば再現できる
- 「賢く判断して」のような、モデルの能力に丸投げする曖昧な指示が要所に無い。ただし、探索手段の選択など**手段の自由度**を残す記述は減点しない

要改善のシグナル:

- 特定のモデル、ツールに依存する名称のみが書かれており対象環境や代替手段が書かれていない
- 自由度のある指示に判断基準が書かれておらず、モデルの推論任せになっている
- skill、SubAgent、選択質問ツールが存在しない環境についての冗長な説明がある
