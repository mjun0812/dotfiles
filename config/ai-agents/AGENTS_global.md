# Global Instructions

## Chat

- 常に日本語で応答すること。
- 文章中に「?」、「？」などの疑問符がある場合や、文章が疑問形の場合には回答のみを行い、編集を行わないこと。
- ユーザーのタイムゾーンはJST (UTC+9)。時刻をユーザーに伝えるときはJSTに変換すること。
- チャットの応答にはtextlintをかけない。

## Development Principles

### Simplicity First

- 求められた以上の機能を追加しない。理論上の堅牢性を高めるためだけに、黙って作業範囲を広げない。
- 仕様やAPIの挙動が分からない部分を推測で実装しない。コードや資料で確かめ、それでも決まらなければユーザーに確認する。
- 起こり得ないケースのためのエラー処理を書かない。スキーマ、コンストラクター、内部の型がすでに保証している値も再検証しない。
- 推測に基づく、または起こる可能性が極めて低い競合状態やセキュリティ上のエッジケースへの対処で複雑さを増やす前に、具体的な失敗の起こり方、起こる可能性、複雑化のコストをユーザーに説明し、同意を得る。

### Code Structure

- 処理は呼び出し箇所にまとめて書く。関数に切り出すのは、再利用する場合、合成可能な形が必要な場合、複雑な処理の境界を隠せる場合、独立した名前で呼び出し側が読みやすくなる場合、検証や前処理を切り出すと正常系の流れが読みやすくなる場合に限る。
- 切り出した関数は、呼び出す関数のすぐ後に定義する。
- 早期returnで分岐を浅くする。returnした後にelseを書かない。
- 一度しか使わない値は、名前が説明を加えない限りインライン化する。
- コメントは、直感的に分かりにくい制約、意外な振る舞い、コードの意図を説明するために書く。自明な代入や制御フロー、T01などの他の資料を参照するコメントは書かない。

### Goal-Driven Execution

- 作業の前に成功条件を決め、検証が通るまで修正と確認を繰り返す。
- 新規機能追加: 設計してから実装する。最後に動作確認を行い、成功条件を満たすことを確認する。
- バグ修正: テストで再現できる場合は、バグを再現するテストを最初に書き、それを通すコードを書き、最後にリファクタリングする。
- リファクタリング: 変更前後でテストが通ることを確認し、変更前後でコードの意図が変わらないことを確認する。
- 性能改善: 最初に既存のコードのボトルネックをhyperfineなどで計測し、目標とする指標を確定する。改善後のコードが目標を満たすことを確認する。
- テストは実際の実装を呼び出して確かめる。実装のロジックをテストコードに写さない。

### Design Principles

- 設計や実装の前に、要件と関連コードを読み、入力から出力までの実際の処理経路を理解する。
- 後方互換性を維持しない。互換レイヤー、フォールバック、移行処理を追加するのではなく、不要になった処理経路は削除する。
- DBの変更は、既存のデータに影響を与えないように慎重に行う。取り返しのつかない変更は行わないこと。
- アーキテクチャ上の判断は長期的な視点で行う。後で置き換えることを前提とした、その場しのぎの実装を採用しない。
- 静的に検査できる規約は、プロンプトやドキュメントではなく、そのリポジトリのlinter設定(ruffなど)かスクリプトの実装、`ast-grep` のルールなど、機械的検査として記述する。

## Project Context

- リポジトリに `.mjun/steering/` が存在する場合、直下の `*.md` をすべてプロジェクトメモリとして読み込むこと。ADR (`docs/adr/` または `.mjun/steering/adr/`) は、過去の判断の理由が必要なときに読むこと。
- リポジトリ直下に用語集 `CONTEXT.md` があればそれを、無ければ `.mjun/CONTEXT.md` を読み、定義された語彙を使うこと。
- リポジトリ内のドキュメントと既存コードの内容が矛盾する場合は、既存コードで実際に採用されている規約や実装方針を優先し、作業中に見つけたドキュメントとコードの不一致を最終回答で報告すること。

## SubAgent

- SubAgentの完了は `wait_agent` で待つ。`sleep` や `list_agents` の繰り返しでpollingしない。
- 実行中のSubAgentへ進捗確認の `send_message` を送らない。結果はSubAgentの最終応答で受け取る。
- SubAgentとして動くときは、親へ途中経過のmessageを送らず、結果は最終応答だけで返す。
- SubAgentのmodelとreasoning effortは、タスクの性質に応じて次の基準で選ぶ。
  - Luna (`xhigh`): 決定的・機械的な定型作業。
  - Luna (`max`): 標準的な実装・調査。
  - Sol (`high`): 設計判断や曖昧な要件(アーキ設計、複数ファイル横断リファクタ、難しいデバッグ)を伴う作業。迷ったらこのモデルを使う。
  - Astra (`xhigh`): Solで解決できなかった作業、またはSolの判断では不十分と分かった作業。

## Tool

- 選択肢付きの質問には `request_user_input` を使用すること。skillや指示に登場する `AskUserQuestion` もこれに読み替える。
- ブラウザ操作では、ログイン状態が必要な操作とユーザーのChromeでの操作には `playwriter` skillを、ログインが不要な操作には `agent-browser` skillを使うこと。
- データファイルの集計・変換・調査には `duckdb` skillを使うこと。プロジェクトのコードに組み込むデータ処理は、そのプロジェクトの既存の依存に従うこと。

## Writing

- チャット以外の文章では半角括弧を使用すること。全角括弧は使わないこと。
- PR・Issueの本文やコメント、HTMLページ、playwriterなどでwebへ入力する文のような日本語の文章は、投稿・公開・入力の前にtextlintにかけ、指摘箇所を文意を保ったまま書き直すこと。commitメッセージやひと言のコメントのような短い文はかけなくてよい。
  - PR・Issueの本文とコメント: `.md` ファイルに書き、`gh` へ `--body-file` で渡す。ファイルの編集時と `gh` の実行時に、hookがtextlintをかける。
  - webへ入力する文: `.md` ファイルに書いてから入力する。ファイルの編集時に、hookがtextlintをかける。
  - HTMLページ: 公開や共有の前に `~/.dotfiles/script/tools/textlint.sh report <file>` にかける。Astroなどのテンプレート (`.astro`・`.vue`・`.tsx` など) に書いた日本語は、ビルドしたHTMLのうち変えたページをかける。どちらも、自分が書いた・変えた文への指摘だけを直す。
- PR・Issue・コメントでは、文章だけでは伝わりにくい内容を図や画像で示すこと。文章の言い換えにしかならない図は入れない。
  - Mermaid: 処理の流れ、依存関係、状態遷移、変更前後の構造。1図1論点で小さく保つ。
  - 画像: UI変更の前後比較、ベンチマークのグラフ、エラーの再現画面。スクリーンショットは `agent-browser` / `playwriter` skillで撮る。
  - 画像は `gh {pr,issue} {create,edit,comment}` の `--attach '<path>#<alt>'` でアップロードする。本文の `![alt](./path.png)` がその位置に差し替わる。リポジトリへはcommitしない。
