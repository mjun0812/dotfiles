# Global Instructions

- 常に日本語で応答すること。
- 文章中に「?」,「？」などの疑問符がある場合や，文章が疑問形の場合には回答のみを行い、編集を行わないこと。
- 常に半角括弧を使用すること。全角括弧は使わないこと。
- ユーザーのタイムゾーンはJST (UTC+9)。時刻をユーザーに伝えるときはJSTに変換すること。

## Development Principles

### シンプルさを最優先する / Simplicity First

問題を解決する最小限のコード。推測による実装はしない。

- 求められた以上の機能を追加しない。
- 起こり得ないケースのための過剰なエラー処理・エラーハンドリングをしない。
- 現在の要件を完全に満たす、最も単純な実装を選ぶ。一度しか使わないコードの抽象化や、将来必要になるかもしれないという理由だけの柔軟性・設定項目・間接層を追加しない。
- 単純化のために、明示された要件、必要な検証、信頼境界での入力検証、データ損失を防ぐ処理、セキュリティ、アクセシビリティを削らない。行数やファイル数の少なさだけで判断しない。

### スタイルの尊重 / Respect style

必要な箇所だけを触る。自分の変更で生じた不要物だけ片付ける。

- 隣接するコード、コメント、フォーマットを「改善」しない。
- 既存のコードベースのディレクトリ構造や実装方針を確認し、それに従って実装してください。
- 自分なら違う書き方をするとしても、既存のスタイルに合わせる。
- すべての変更行は、ユーザーの依頼に直接結びついていること。

### ゴール駆動の実行 / Goal-Driven Execution

成功条件を定義する。検証されるまでループする。

- バグ修正: バグを再現するテストを書き、それを通す
- バグ修正では、変更対象の呼び出し元と共有処理を調べ、報告された経路以外にも同じ原因が影響するかを確認する。共通原因があれば、その不変条件を所有する箇所で修正する。必要な修正が許可された範囲を越える場合は、範囲を広げる前に報告する。
- バリデーション追加: 不正な入力のテストを書き、それを通す
- リファクタ: 変更前後でテストが通ることを確認する

### 設計方針 / Design Principles

- 設計や実装の前に、要件と関連コードを読み、入力から出力までの実際の処理経路を理解する。
- 既存コード、標準ライブラリ、プラットフォーム機能、導入済み依存の順に、要件を満たす手段を確認する。既存の実装方針と信頼性も考慮し、要件を満たす単純な手段が見つかれば、追加の比較調査や独自設計を行わない。いずれでも足りない場合は、一般的な機能を独自に再実装せず、実績があり継続的に保守されているライブラリの導入を優先する。標準機能を使うために、既存ライブラリが担う処理を独自に再実装しない。
- 外部調査は未解決の判断に必要な範囲で行い、実績ある製品の解決方法や実証済みのパターンを優先する。
- 後方互換性を維持しない。互換レイヤー、フォールバック、移行処理を追加するのではなく、不要になった処理経路は削除する。ただし、DBの変更は、既存のデータに影響を与えないように慎重に行う。取り返しのつかない変更は行わないこと。
- コンポーネントをモジュール化し、それぞれの責務や関心事を明確に分離する。
- アーキテクチャ上の判断は長期的な視点で行う。後で置き換えることを前提とした、その場しのぎの実装を採用しない。
- 静的に検査できる規約は、プロンプトやドキュメントではなく、そのリポジトリのlinter設定(ruffなど)か `ast-grep` のルールとして記述する。

## SubAgent

- SubAgentはGPT-5.6のモデルを使用すること。
- SubAgentへ移譲する際は、タスクの性質に応じて呼び出し時にmodelを指定する
  - Luna: 決定的・機械的な定型作業や標準的な実装・調査。迷ったらこのモデルを使う。
  - Sol: 設計判断や曖昧な要件(アーキ設計、複数ファイル横断リファクタ、難しいデバッグ)を伴う作業。
- SubAgentの完了を待つときは `wait_agent` をtimeout 10分以上で呼ぶ。`sleep` や `list_agents` の繰り返しでpollingしない。
- 実行中のSubAgentへ進捗確認の `send_message` を送らない。結果はSubAgentの最終応答で受け取る。
- SubAgentとして動くときは、親へ途中経過のmessageを送らず、結果は最終応答だけで返す。

## Tool

- skillや指示に登場する `AskUserQuestion` は `request_user_input` に読み替えること。
- skillや指示に登場する `superpowers:<name>` は、APMで導入した `<name>` skillに読み替えること (例: `superpowers:writing-skills` → `writing-skills`)。
- `retrospective-codify` skillの書き出し先は次に読み替えること。
  - グローバルルール: `~/.dotfiles/config/ai-agents/claude/CLAUDE.md` と `~/.dotfiles/config/ai-agents/AGENTS_global.md` の両方
  - 言語別ルール: `~/.dotfiles/config/ai-agents/claude/rules/` の該当ファイルと、`AGENTS_global.md` の同名の節の両方
  - 新規skill: `mjun0812/skills` リポジトリ

## Steering

- リポジトリに `.mjun/steering/` が存在する場合、配下の `*.md` をすべてプロジェクトメモリとして読み込むこと。
- coreファイルは `product.md` (目的・価値)、`tech.md` (技術スタック・規約)、`structure.md` (構成パターン)。ドメイン別のcustomファイルもcoreと同格に扱うこと。
- core / custom steeringの作成・更新は `mjun-steering` skillで行うこと。決定記録は同skillの記録規則に従い、判断を行ったskillがその場で1件1ファイルとして追加する。

## Glossary and ADR

- リポジトリに用語集 `CONTEXT.md` (repo直下にあればそれ、無ければ `.mjun/CONTEXT.md`) が存在する場合は読み込み、定義された語彙を使うこと。
- 決定記録とADRは1件1ファイル (`NNNN-<slug>.md`) としてGit管理へ移行済みなら `docs/adr/`、それ以外は `.mjun/steering/adr/` に集約し、存在すれば読み込む。StatusとScopeを確認し、tentative・supersededや他specだけの判断を現在の共通規約として適用しない。適用対象のacceptedな決定に反する変更は実装前にユーザーへ確認する。

## Git

GitHub操作は必ず `git, gh` CLIで行うこと。GitHub connector/pluginやMCPのGitHubツールは使用しない。

- `gh` コマンドでCIやPRの完了などを長時間待機する場合は、Rate Limitの消費を抑えるため、適切な間隔を空けて明示的に状態を再取得すること。

## Python

- 環境およびパッケージ管理には `uv` を使用すること。
- コードのフォーマットには `uvx ruff format`を使ってください．
- コードのリンターには`uvx ruff check --fix` を使用すること。
- コードの型チェックには`uvx ty check` を使用すること。
- 文字列リテラルに変数を埋め込むときは，f-stringを使ってください．
- SQLAlchemy ORM は **2.0 スタイル**の記法を使用してください。
- **型ヒント**を必ず記述してください。Anyの使用は避け、具体的な型を指定してください。
- 全ての関数やクラスにDocstringを記述してください．記述スタイルは**Google スタイル**で記述してください。

## Markdown

- Formatterに`oxfmt`を使うこと
- 英数字と日本語の間、および半角括弧 `()` の外側に半角スペースを入れないこと。inline codeの前後には入れてよい。コードブロックの中は対象外
  - 良い例: MLflowサーバをECS(arm64)で動かす。`mlflow-server` のrepoを使う。
  - 悪い例: MLflow サーバを ECS (arm64) で動かす。
- 区切り線 `---` を多用しないこと。節の区切りは見出しで表す。文書の中で性質が大きく変わる境界(例: 現行の手順と旧構成の記録の間)にだけ使う
- コマンドがbashとzshで異なる場合は、同じコードブロックに `# bash` と `# zsh` のコメントで分けて両方を書くこと。共通の部分は1つにまとめる

## ShellScript

- シェルスクリプトのフォーマットには `shfmt` を使用してください。
- シェルスクリプトのリンターには `shellcheck` を使用してください。
- シェルスクリプトは関数をあまり使用せず、シンプルで手続き型な構造にしてください。
- 関数を使用する場合は、3回以上呼び出されるコードに対してのみ使用してください。

## Lua

- コードのフォーマットには `stylua` を使用すること。
- リポジトリに `.editorconfig` または `stylua.toml` (`.stylua.toml`) がある場合はその設定を優先し、オプションを付けずに `stylua .` を実行すること。
- どちらも無い場合は、インデント2スペース・1行120桁をオプションで明示すること: `stylua --indent-type Spaces --indent-width 2 --column-width 120 .` (`--check` を付けると書き換えずに未整形のファイルだけ報告する)。

## Skill

- Agent skill を作成・編集するときは、コマンド例を最小限にする。
- コマンド例は、次のいずれかを明確にする場合にだけ追加する。
  - 入力・出力の形式
  - 操作の順序
  - 境界ケース
- 網羅性のためだけに具体例を追加しない。

## Jupyter Notebook

- `.ipynb`をraw JSONとして編集しない。
- Jupytextのpaired `py:percent` fileがある場合は`.py`をGit上の正本とし、通常の編集は`.py`へ行う。
- JupyterLabを使わないcell-level操作には`nb-cli`のlocal modeを使う。
- 同じNotebookをJupytext、`nb-cli`から同時に書き換えない。
