# Global Instructions

- 常に日本語で応答すること。
- 文章中に「?」,「？」などの疑問符がある場合や，文章が疑問形の場合には回答のみを行い、編集を行わないこと。
- 常に半角括弧を使用すること。全角括弧は使わないこと。
- ユーザーのタイムゾーンはJST (UTC+9)。時刻をユーザーに伝えるときはJSTに変換すること。

## Development Principles

### シンプルさを最優先する / Simplicity First

問題を解決する最小限のコード。推測による実装はしない。

- 求められた以上の機能を追加しない。
- 一度しか使わないコードのために抽象化しない。
- 求められていない「柔軟性」や「設定可能性」を追加しない。
- 起こり得ないケースのための過剰なエラー処理・エラーハンドリングをしない。
- 現在の要件を完全に満たす、最も単純な実装を選ぶ。将来必要になるかもしれないという理由だけで、抽象化、設定項目、間接層を追加しない。

### スタイルの尊重 / Respect style

必要な箇所だけを触る。自分の変更で生じた不要物だけ片付ける。

- 隣接するコード、コメント、フォーマットを「改善」しない。
- 既存のコードベースのディレクトリ構造や実装方針を確認し、それに従って実装してください。
- 自分なら違う書き方をするとしても、既存のスタイルに合わせる。
- すべての変更行は、ユーザーの依頼に直接結びついていること。

### ゴール駆動の実行 / Goal-Driven Execution

成功条件を定義する。検証されるまでループする。

- バグ修正: バグを再現するテストを書き、それを通す
- バリデーション追加: 不正な入力のテストを書き、それを通す
- リファクタ: 変更前後でテストが通ることを確認する

### 設計方針 / Design Principles

- 解決策を設計する前に、既存の実績ある製品が同じ問題をどのように解決しているかを調査する。ゼロから独自の方法を考案するのではなく、実証済みのパターンや慣例を優先する。
- 後方互換性を維持しない。互換レイヤー、フォールバック、移行処理を追加するのではなく、不要になった処理経路は削除する。ただし、DBの変更は、既存のデータに影響を与えないように慎重に行う。取り返しのつかない変更は行わないこと。
- コンポーネントをモジュール化し、それぞれの責務や関心事を明確に分離する。
- 全体の複雑さを減らしたり、信頼性を向上させたりできる場合は、実績があり継続的に保守されているライブラリを優先する。明確な理由がない限り、一般的な機能を独自に再実装しない。
- アーキテクチャ上の判断は長期的な視点で行う。後で置き換えることを前提とした、その場しのぎの実装を採用しない。

## SubAgent

- FableはSubAgentとして使用しない。
- SubAgentへ移譲する際は、タスクの性質に応じて呼び出し時にmodelを指定する
  - haiku: 決定的・機械的な定型作業(フォーマット変換、grep要約、テンプレ生成)
  - sonnet: 標準的な実装・調査。(関数/テスト作成、典型バグ修正、レビュー)。迷ったらこのモデルを使う。
  - opus: 設計判断や曖昧な要件(アーキ設計、複数ファイル横断リファクタ、難しいデバッグ)
  - codex: Codex CLIへの移譲。modelではなくsubagent_typeで指定する。
    - codex-worker: ユーザーが明示的にCodexへの作業委譲を依頼したときのみ使用する
    - codex:codex-rescue: 行き詰まったとき、セカンドオピニオンや別実装案が欲しいときに自発的に使用してよい

## Tool

- skillや指示に登場する `request_user_input` は `AskUserQuestion` に読み替えること。
- ブラウザ操作には優先的に `agent-browser` skillを使うこと。通信解析・performance trace・heap snapshotなど、chrome-devtools MCPにしかない機能が必要なときだけ `chrome-devtools` MCPを使う。
- `Web Search`:
  - 可能な限り、最新の公式ドキュメントや一次情報源を優先して参照すること。
  - 会話している言語に関わらず、英語・日本語の両方で検索を行ってください。

## Steering

- リポジトリに `.mjun/steering/` が存在する場合、配下の `*.md` をすべてプロジェクトメモリとして読み込むこと。
- coreファイルは `product.md` (目的・価値)、`tech.md` (技術スタック・規約)、`structure.md` (構成パターン)。ドメイン別のcustomファイルもcoreと同格に扱うこと。
- steeringの作成・更新は `steering` skillで行うこと。手動で書き換えない。

## Versioning

- バージョン番号を扱う際は Semantic Versioning 2.0.0 に従うこと。

## Git

- コミットメッセージは常に Conventional Commits 形式に従うこと。
- 2行目は必ず空行とし、コミットの説明は3行目から記述すること。
- Gitタグを使用する際は "v1.0.0" や "v2.1.3" といったSemantic Versioningの形式を使用すること。
- コミットメッセージは変更内容を具体的に記述すること。「レビュー対応」「修正」「更新」のような曖昧な表現は禁止。何を・なぜ変更したかが分かるメッセージにすること。
- `gh` コマンドでCIやPRの完了などを長時間待機する場合は、Rate Limitの消費を抑えるため、適切な間隔を空けて明示的に状態を再取得すること。
