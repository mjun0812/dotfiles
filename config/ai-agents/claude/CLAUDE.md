# Global Instructions

- 常に日本語で応答すること。
- 文章中に「?」,「？」などの疑問符がある場合や，文章が疑問形の場合には回答のみを行い、編集を行わないこと。
- 常に半角括弧を使用すること。全角括弧は使わないこと。
- ユーザーのタイムゾーンはJST (UTC+9)。時刻をユーザーに伝えるときはJSTに変換すること。

## Development Principles

### Simplicity First

問題を解決する最小限のコード。推測による実装はしない。

- 求められた以上の機能を追加しない。
- 起こり得ないケースのための過剰なエラー処理・エラーハンドリングをしない。
- 現在の要件を完全に満たす、最も単純な実装を選ぶ。一度しか使わないコードの抽象化や、将来必要になるかもしれないという理由だけの柔軟性・設定項目・間接層を追加しない。
- 単純化のために、明示された要件、必要な検証、信頼境界での入力検証、データ損失を防ぐ処理、セキュリティ、アクセシビリティを削らない。行数やファイル数の少なさだけで判断しない。

### Respect style

必要な箇所だけを触る。自分の変更で生じた不要物だけ片付ける。

- 隣接するコード、コメント、フォーマットを「改善」しない。
- 既存のコードベースのディレクトリ構造や実装方針を確認し、それに従って実装してください。
- 自分なら違う書き方をするとしても、既存のスタイルに合わせる。
- すべての変更行は、ユーザーの依頼に直接結びついていること。

### Goal-Driven Execution

成功条件を定義する。検証されるまでループする。

- バグ修正: バグを再現するテストを書き、それを通す
- バグ修正では、変更対象の呼び出し元と共有処理を調べ、報告された経路以外にも同じ原因が影響するかを確認する。共通原因があれば、その不変条件を所有する箇所で修正する。必要な修正が許可された範囲を越える場合は、範囲を広げる前に報告する。
- バリデーション追加: 不正な入力のテストを書き、それを通す
- リファクタ: 変更前後でテストが通ることを確認する

### Design Principles

- 設計や実装の前に、要件と関連コードを読み、入力から出力までの実際の処理経路を理解する。
- 既存コード、標準ライブラリ、プラットフォーム機能、導入済み依存の順に、要件を満たす手段を確認する。既存の実装方針と信頼性も考慮し、要件を満たす単純な手段が見つかれば、追加の比較調査や独自設計を行わない。いずれでも足りない場合は、一般的な機能を独自に再実装せず、実績があり継続的に保守されているライブラリの導入を優先する。標準機能を使うために、既存ライブラリが担う処理を独自に再実装しない。
- 外部調査は未解決の判断に必要な範囲で行い、実績ある製品の解決方法や実証済みのパターンを優先する。
- 後方互換性を維持しない。互換レイヤー、フォールバック、移行処理を追加するのではなく、不要になった処理経路は削除する。ただし、DBの変更は、既存のデータに影響を与えないように慎重に行う。取り返しのつかない変更は行わないこと。
- コンポーネントをモジュール化し、それぞれの責務や関心事を明確に分離する。
- アーキテクチャ上の判断は長期的な視点で行う。後で置き換えることを前提とした、その場しのぎの実装を採用しない。
- 静的に検査できる規約は、プロンプトやドキュメントではなく、そのリポジトリのlinter設定(ruffなど)か `ast-grep` のルールとして記述する。

## SubAgent

- FableはSubAgentとして使用しない。
- SubAgentへ移譲する際は、タスクの性質に応じて呼び出し時にmodelを指定する
  - haiku: 決定的・機械的な定型作業(フォーマット変換、要約、テンプレ生成)
  - sonnet: 標準的な実装・調査。(関数/テスト作成、典型バグ修正、レビュー)。迷ったらこのモデルを使う。
  - opus: 設計判断や曖昧な要件(アーキ設計、複数ファイル横断リファクタ、難しいデバッグ)

## Steering

- リポジトリに `.mjun/steering/` が存在する場合、配下の `*.md` をすべてプロジェクトメモリとして読み込むこと。
- coreファイルは `product.md` (目的・価値)、`tech.md` (技術スタック・規約)、`structure.md` (構成パターン)。ドメイン別のcustomファイルもcoreと同格に扱うこと。
- core / custom steeringの作成・更新は `mjun-steering` skillで行うこと。決定記録は同skillの記録規則に従い、判断を行ったskillがその場で1件1ファイルとして追加する。

## Glossary and ADR

- リポジトリに用語集 `CONTEXT.md` (repo直下にあればそれ、無ければ `.mjun/CONTEXT.md`) が存在する場合は読み込み、定義された語彙を使うこと。
- 決定記録とADRは1件1ファイル (`NNNN-<slug>.md`) としてGit管理へ移行済みなら `docs/adr/`、それ以外は `.mjun/steering/adr/` に集約し、存在すれば読み込む。StatusとScopeを確認し、tentative・supersededや他specだけの判断を現在の共通規約として適用しない。適用対象のacceptedな決定に反する変更は実装前にユーザーへ確認する。

## Git

GitHub操作は必ず `git, gh` CLIで行うこと。GitHub connector/pluginやMCPのGitHubツールは使用しない。

- `gh` コマンドでCIやPRの完了などを長時間待機する場合は、Rate Limitの消費を抑えるため、適切な間隔を空けて明示的に状態を再取得すること。
